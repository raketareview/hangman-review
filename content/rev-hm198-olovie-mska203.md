## ЗАМЕЧАНИЯ

**1. Нейминг**

- Если в проекте есть класс `Word`, то все переменные с именем, включающим это название, должны быть экземплярами этого класса.  

Когда разные концепции называются одним и тем же именем, это приводит к путанице
```java
public class Word {
  //...

  public String getMaskedWord() {...} <-- Этот метод называется "вернуть Word". Но возвращает String  
}

//ПРАВИЛЬНО:
public class Word {
  //...

  public String getMask() {...} 
}
```

- Название методов должно быть глаголом (кроме некоторых исключений, которые в данном случае не важны).  
Это название - существительное
```java
String wordChoice(List<String> words)

//ПРАВИЛЬНО:
String chooseWord(List<String> words)
```

- Название методов должно быть глаголом 
Это название - существительное
```java
List<String> wordListCreator()

//ПРАВИЛЬНО:
List<String> createWords()
```
Но так называть тоже нельзя потому что...

- ...если у тебя в проекте есть класс "Word", то все методы с названием, включающим это слово, должны работать с экземплярами этого класса.

Поэтому класс "WordProvider" должен провайдировать экземпляры `Word`, а не `String`.  
Ну, или называться по-другому
```java
public class Word {...}

public class WordProvider {
  //...
  public static List<String> wordListCreator() throws Exception {...}

  public static String wordChoice(List<String> words) {...}
}

//ПРАВИЛЬНО:
public class Dictionary {
  //...
  public static List<String> read() {
    //читает строки из файла
  }

  public static String getRandom(List<String> lines) {...}
}
```
Иначе термин "Word" у тебя в проекте приходится понимать в двух разных контекстах.

- Формулируй точнее
```java
char askForLetter() {
  //получает букву от юзера    
}

//ПРАВИЛЬНО:
char inputLetter()
```

- Название путает.

Не называй метод "run" если он не переопределяет `Runnable.run()` - название этого метода ассоциируется с этим стандартным интерфейсом и применением потоков.  
Здесь этот метод не имеет отношения к `Runnable.run()`
```java
public class ApplicationController {
  public void run() {...}
  //...
}

//ПРАВИЛЬНО:
start(), go(), execute(), perform() 
```
*Oracle Java code conventions, part."Naming conventions"*

**2. Нарушение конвенции кода**

- Скобочки.

В любой ситуации выделяй тело блока скобочками, даже если тело состоит из одной строки  
```java
if (line.equals("1")) return true;
if (line.equals("2")) return false;

//ПРАВИЛЬНО:
if (line.equals("1")) {
  return true;
}

if (line.equals("2")) {
  return false;
}
```
Исключение - метод equals(), там де-факто разрешается после `if` не выделять блоки скобочками. 

*"Oracle Java Code Conventions"* 

**3. Exceptions**

- Не бросай базовый exception. Конкретизируй ситуацию- бросай то исключение, которое подходит под этот конкретный случай
```java
throw new RuntimeException("Не удалось начать новую игру", e);
```
*Хорстманн "Java. Библиотека профессионала", т.1, гл.11*
```java
"Не ограничивайтесь генерацией RuntimeException. 
Найдите подходящий подкласс или создайте собственный." - Хорстманн
```

- Текст в Exception всегда должен быть на английском языке.
```java
if (value == null || value.isBlank()) {
  throw new IllegalArgumentException("Слово не может быть пустым"); <-- Неправильно: сообщение в исключении не на английском языке
}
```
Исключение- это не просто телеграмма, которая летит сквозь слои.

У exception особое назначение- если исключение вылетит и не будет перехвачено внутри программы, то аварийно прекратит выполнение программы.  
Тогда на экране будет распечатано сообщение эксепшена, и это сообщение должно быть понятно сисадмину в любой точке планеты.  
А значит, сообщение должно быть на английском.

Интерпретация исключения и перевод его на локальный язык должны происходить там, где это соответствует архитектуре программы.  
Или не происходить вовсе, если исключение не планируется перехватывать.

- Проверяемые исключения перехватывай в точке их возникновения и заменяй на непроверяемые. 

Проброс исключений в сигнатуре методов захламляет код.  
Поэтому заменяй проверяемые исключения на непроверяемые  
```java
public static List<String> wordListCreator() throws Exception {...}

//ПРАВИЛЬНО:
public static List<String> wordListCreator() {...}
```

**4. Форматирование**

- Форматирование строк.

Если нужно печатать или создавать строку с более чем одним подстановочным значением или значение вставляется внутрь сообщения, 
используй форматирование - тогда сразу будет виден весь шаблон сообщения
```java
System.out.println("*** Поражение. Слово было: " + game.getRevealedWord() + " ***");

//ПРАВИЛЬНО:
System.out.printf("*** Поражение. Слово было: '%s' ***  \n", game.getRevealedWord());
```

- Если всё равно одну инструкцию форматируешь на две строки, то лучше делай так
```java
throw new IllegalArgumentException(
  "Буквы '" + letter + "' нет в слове");

//ПРАВИЛЬНО:
String message = "Буквы '%c' нет в слове".formatted(letter);  //тоже 2 строки, но читается приятнее
throw new IllegalArgumentException(message);
```

- Если там внутри так много всяких сложных конструкций, создавай поясняющие переменные:
```java
throw new IllegalStateException(
    "Число стадий (" + STAGES.length + ") не совпадает с MAX_MISTAKES + 1 ("
        + (MAX_MISTAKES + 1) + ")");

//ПРАВИЛЬНО:
String message = "Стадия повешения превышает MAX_MISTAKES + 1 (%d): %d".formatted(MAX_MISTAKES + 1, STAGES.length);
throw new IllegalStateException(message);
```
Естественно, месседж в исключении должен быть на англ.

**5. class Word**

+ 👍 Хорошо, что выявил сущность "Слово" и сделал её классом. 

Скрытые и открытые буквы, а также методы для работы с ними (открыть букву, проверить полное открытие слова) являют из себя отдельную объектно-ориентированную сущность.

- Нарушение инкапсуляции.

Доступ к полям класса, тем более изменяемым, должен происходить не напрямую, а через методы.  
Например, геттеры и сеттеры
```java
public static String value;
```  

- Нарушение ООП дизайна.

Это поле не должно быть static
```java
public class Word {
  public static String value;
  //...
}

//ПРАВИЛЬНО:
public class Word {
  public final String value;
  //...
}
```

Статические поля в ООП программе нужно применять очень осторожно. 
Потому что сама идея классов состоит в том, что у класса может быть несколько экземпляров одновременно. 
И при этом все они должны корректно работать.

В данном случае если в проекте будет существовать несколько экземпляров класса одновременно, они будут работать некорректно. 
Потому что будут одновременно вносить изменения в одно и то же статическое поле.

И тут вопрос не в том, должно ли *конкретно в этом* проекте быть два экземпляра одного класса, или не должно. 
Если класс не утилитный, не синглтон и можно создать несколько его экземпляров, то по умолчанию мы признаем, что его экземпляров в проекте может быть более одного.

- Конструктор должен стоять выше остальных методов.

- Если тут и вводить поясняющую переменную, то нужно делать это по-другому 
```java
boolean contains = value.contains(Character.toString(normalizeChar(letter)));
return contains;

//ПРАВИЛЬНО:
String normalizeLetter = Character.toString(normalizeChar(letter);
return value.contains(normalizeLetter);
```

+ 👍 В целом класс хороший. С точки зрения SOLID - вообще замечательный.

**7. class GallowsRenderer**

```java

```
Всегда можно найти альтернативы блоку статик. Например, вызывать статические методы.

public static final int MAX_MISTAKES = 6;

static {
  if (STAGES.length != MAX_MISTAKES + 1) {

**9. class Game**

- Позиционирование.

Этот класс - что-то непонятное.

С одной стороны, он похож на движок игры.

Движок это вся игровая логика без взаимодействия с представлением.  
То есть, движок это модель.  
Игровая логика с взаимодействием с представлением в таких случаях выносится в отдельный контроллер.  

Здесь, вроде бы, в целом всё так и есть, но дополнительно хранится одно представление: `GallowsRenderer`.  
Таким образом, из внятного модели-движка, класс становится чем-то невнятным.

Если убрать отсюда рендерер, то класс будет норм.

- Нарушение SRP.

Этот класс не должен сам куда-то лезть и добывать слово для игры.  
Слово для игры он должен получать в конструктор
```java
public class Game {
  //...

  public Game(GallowsRenderer renderer) {...}

  public void startNewGame(String ) {
    try {
      List<String> words = WordProvider.wordListCreator(); 
      String raw = WordProvider.wordChoice(words);
      //...
    }
  }
}

//ПРАВИЛЬНО ЛИБО ТАК:
public class Game {
  //...

  public Game(Word word) {...}

  public void startNewGame() {...}
}

//ЛИБО ТАК:
public class Game {
  //...

  public Game() {...}

  public void startNewGame(Word word) {...}
}
```

Потому что так класс будет более универсальный и можно будет создавать разные майн-классы (игровые конфигурации):
```java
public class TestMain {
  public static void main(String[] args) {
    GallowsRenderer renderer = new GallowsRenderer();
    ConsoleUI ui = new ConsoleUI();
    Word word = new Word("кавалькада");
    Game game = new Game(word); 

    ApplicationController controller = new ApplicationController(game, renderer, ui);
    controller.run();
}
```
