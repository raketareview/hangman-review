**1. Нейминг**

- Аббревиатуры в названиях лучше писать так же, как и другие слова
```java
enum HangmanASCII

//ЛУЧШЕ:
enum HangmanAscii
```
Например, какое название понятнее: HTTPURL или HttpUrl?  
*Блох "Java. Эффективное программирование", изд.3, гл.9.12.*

- Значения енама это константы, а константы нужно писать UPPER_SNAKE
```java
public enum HangmanASCII {
  Stage0(...),
  Stage1(...),
  //...
}

//ПРАВИЛЬНО:
public enum HangmanASCII {
  STAGE_0(...),
  STAGE_1(...),
  //...
}
```

- Не усложняй
```java
public class MenuItem {
  private final String text;
  private final Runnable action;

  public MenuItem(String newText, Runnable newAction) {
    text = newText;
    action = newAction;
  }
  //...
}

//ПРАВИЛЬНО:
public class MenuItem {
  private final String text;
  private final Runnable action;

  public MenuItem(String text, Runnable action) {
    this.text = text;
    this.action = action;
  }
  //...
}
```

- Не используй слово "new" когда создаешь что-то новое.

Во-первых `new` это зарезервированное слово и не нужно его везде использовать всуе.  
Во-вторых, всё что ты создаешь, будет новое, а значит всё нужно подписывать "new" и это станет словом-паразитом.

Есть много альтернативных слов для обозначения создания чего-то нового
```java
public void newRound() 

//ПРАВИЛЬНО:
createRound(), makeRound() 
```

- Разные концепции называются одним названием
```java
public String getWord(int index)
private List<Character> word;
```

Определись, что у тебя в проекте должно называться словом "word"- строка или список букв.  
А для другого придумай альтернативные названия, например:
```java
public String getWord(int index)
private List<Character> letters;
```

**2. При прочих равных, нужно использовать примитивный тип, а не класс-обертку**
```java
public Character getWordLetter(int index) 
public void addError(Character letter)

//ПРАВИЛЬНО:
public char getWordLetter(int index) 
public void addError(char letter)
```
Для применения класса-обертки над примитивным типом данных, должна быть какая-то причина.  
Здесь использование обертки не дает ничего большего по сравнению с примитивом.  
*Блох "Java. Эффективное программирование", изд.3, гл.9.5*
```java
"Предпочитайте примитивные типы упакованным примитивным типам" - Блох.
```

- Так выглядит намного естественнее:
```java
for (Character let : word) {...}

//ЛУЧШЕ:
for (Character c : word) {...}
```
По крайней мере, не приходится задумываться, почему керектер вдруг стал летом и что такое вообще "let".

- Да просто назови или `get()` или `input()`, зачем здесь эта тавтология
```java
public class InputHandler {
  public <T> T getInput(...)
}

//ПРАВИЛЬНО:
public class InputHandler {
  public <T> T get(...)

```

- Если метод называется "проверить"(check), то результат этой проверки должен быть boolean.  
Если метод не возвращает boolean, значит он не выполняет проверку и не должен так называться
```java

```

**3. Если в блоке if есть return(break, continue, throw, exit и т.д.), то else не пишется** 

В этом случае неважно, будет else или нет, так как программа будет работать одинаково, а код без else будет выглядеть читабельней
```java
if (validator.isValid(value, type)) {
  return parser.parse(value, type);
} else {
  printer.print("Ошибка ввода. ");
}

//ПРАВИЛЬНО:
if (validator.isValid(value, type)) {
  return parser.parse(value, type);
} 
printer.print("Ошибка ввода. ");
```

**4. Exceptions**

- Текст в exception всегда должен быть на английском языке.
```java
throw new IllegalArgumentException("Значение не может быть null или пустым");  <-- Неправильно: сообщение в исключении не на английском языке
```
Исключение это не просто телеграмма, которая летит сквозь слои.

У exception особое назначение- если исключение вылетит и не будет перехвачено внутри программы, то аварийно прекратит выполнение программы.  
Тогда на экране будет распечатано сообщение эксепшена, и это сообщение должно быть понятно сисадмину в любой точке планеты.  
А значит, сообщение должно быть на английском.

Интерпретация исключения и перевод его на локальный язык должны происходить там, где это соответствует архитектуре программы.  
Или не происходить вовсе, если исключение не планируется перехватывать.

**5. Форматирование**

- Форматирование строк.

Если нужно печатать или создавать строку с более чем одним подстановочным значением или значение вставляется внутрь сообщения, 
используй форматирование- тогда сразу будет виден весь шаблон
```java
System.out.println("Ошибки (" + errorsCount + "): " + lettersString);

printer.println("Неправильно! Буквы '" + letter + "' нет в слове.");

//ПРАВИЛЬНО:
System.out.printf("Ошибки (%d): %s  %n", errorsCount, lettersString);

String message = "Неправильно! Буквы '%c' нет в слове.".formatted(letter);
printer.println(message);
```

- Это же твой самодельный принтер, добавь туда перегруженный метод `println()`, чтобы код был красивее
```java
printer.println("");

//ПРАВИЛЬНО:
printer.println();
```

### Пакет model

Судя по названию, в этом пакете должны быть модели.  
В ООП модель это класс, который может содержать данные и логику и не должен зависеть от представления.  
Главный признак класса модели - такой класс должен быть создан так, чтобы мог одинаково работать в любой визуальной среде: 
в консольной программе, андроиде, программе с Windows UI и даже на аркадном автомате с лампочками.

Если класс-модель нужно переделывать для каждой новой визуальной среды, значит класс не соответствует требованиям модели.

Не все классы в этом пакете являются моделями.

**6. enum HangmanASCII**

- Это не модель.

Здесь хранятся картинки в виде псевдографики, которая актуальна только для одного типа представления- консоли.  
Картинки любого формата не являются моделями. Если говорить о слоях, то это слой представления - `view`.

- Неправильное использование enum. 

Если хранить картинки тупо в массиве, это будет правильнее.  
Сейчас картинки используются через индусский код так:
```java
public class Printer {
  //...
  public void printHangmanArt(int errors) {
    String art = switch (errors) {
      case 0 -> HangmanASCII.Stage0.getArt();
      case 1 -> HangmanASCII.Stage1.getArt();
      //...
      default -> HangmanASCII.Stage6.getArt();
    };
    System.out.println(art);
  }
}
```

Если картинки просто хранить в константе, это будет проще и понятнее:
```java
public final class HangmanAscii {
  private static final String[] PICTURES = {
      """
    -----   
    |       
    |       
    |       
    ------- 
    """,
      """
     -----   
     |   |   
     |   O   
     |       
     ------- 
     """
      ,
      // more pics
  };
  
  private HangmanAscii(){}
}

public class Printer {
  //...
  public void printHangmanArt(int errors) {
    String picture = HangmanASCII.PICTURES[errors];
    System.out.println(picture);
  }
}
```

Фактически, сейчас неправильное хранение картинок в виде енама заставило использовать для распечатке избыточный алгоритм через switch-case.

public class MenuItem {

**8. class Round**

+ 👍 ЧТО-ТО ТИПА движка игры, то есть движок одного игрового раунда. Движок это хорошо.

Движок это вся игровая логика без взаимодействия с представлением.  
Игровая логика с взаимодействием с представлением в таких случаях выносится в отдельный контроллер.  

В данном случае это не совсем движок игры и я даже не уверен, является ли это попыткой написать именно движок игры.  
Потому что настоящий движок игры содержал бы в себе больше логики собственно игрового процесса.  
Вернее, он содержал бы весь алгоритм игрового процесса, который бы не зависел от представления.

Например, в движке должен бы находиться(исключительно по моему скромному мнению и его я в данном случае не навязываю) метод, в который ты бы кидал введенную букву.  
А этот метод по своему хитрому алгоритму проверял бы, есть такая буква в слове, нет и всё такое прочее.  
И по результатам этих действий, изменял бы своё состояние- увеличивал бы счетчик ошибок, пополнял список введенных букв, открывал букву в маске.  
И делал бы это САМ, а не как сейчас- через сеттеры, за которые дёргает клиент. 

То есть сейчас это выглядит так:
```java
public class Round {
  //...

  public Set<Character> getUsedLetters() {
    return new HashSet<>(usedLetters);
  }

  public void addUsedLetter(Character letter) {
    usedLetters.add(letter);
  }

  public int getErrors() {
    return errorsCount;
  }

  public void addError(Character letter) {
    errorLetters.add(letter);
    errorsCount++;
  }
}
```

А движок бы работал примерно так:
```java
public class Round {
  //...

  public void execute(char letter) {
    //если буква неправильная - увеличить счетчик ошибок и добавить букву в список неправильных
    //если буква правильная - добавить букву в список правильных
    //остальная логика совершения хода, которая не зависит от представления. 
  }

  public Set<Character> getUsedLetters() {
    return new HashSet<>(usedLetters);
  }

  //приватный метод!
  private void addUsedLetter(Character letter) {
    usedLetters.add(letter);
  }

  public int getErrors() {
    return errorsCount;
  }

  //приватный метод!
  private void addError(Character letter) {
    errorLetters.add(letter);
    errorsCount++;
  }

  //oths methods
}
```

Поэтому сейчас этот класс с одной стороны выглядит так, будто ты хотел написать движок.  
С другой стороны это выглядит как контейнер с функциями в стиле процедурного программирования, 
куда ты вынес все методы, которые как-то связаны с проблемами выполнения хода.

Короче, здесь первична именно мотивация твоего решения при создании этого класса.

Если ты накидал сюда методы без какой-то определенной идеи, то класс получился похожим на процедурный модуль.  
И тогда нужно подумать о перераспределении ответственностей между классами. То есть, подумать об объектно-ориентированной декомпозиции.

- Неправильная начальная инициализация данных в классе.

Сейчас начальная инициализация делается через сеттер:
```java
Round round = new Round();
newRound();

public void newRound() {
  round.clear();
  round.setWord(getRandomWord());
}
```

Правильно в данном случае инициализировать через конструктор:
```java
String word = getRandomWord();
Round round = new Round(word);
```

Но тогда не удастся сбрасывать состояние раунда через `clear()`, заново его устанавливать через сеттер и многократно использовать *один и тот же* экземпляр для разных слов?

Да, но этого и не надо. Если тебе нужен новый раунд, то не переиспользуй текущий, а просто создай новый экземпляр:
```java
String word = getRandomWord();
Round round = new Round(word);
```
Не бойся пересоздавать объекты, это нормальный ООП подход.

- Распределение ответственностей.

Раунд уже содержит данные для игры и сложное поведение: `clear()`, `boolean hasLetter(Character letter)`, `void addError(Character letter)`.

Поэтому не вижу причин, почему он не может самостоятельно определять состояние раунда.  
Сейчас так:
```java
public class Round {
  //...

  public boolean isWin() {
    return isWin;
  }

  public void setWin(boolean win) {
    isWin = win;
  }
}
```

Правильно так:
```java
public class Round {
  //...

  public boolean isLose() {
    return errorsCount >= MAX_ERROR;
  }

  public boolean isWin() {
    //return true если слово открыто
  }
}
```

Сейчас определением состояния раунда занимается его контроллер.  
Это неправильно потому что контроллер должен быть тонким и содержать в себе только ту логику, которую нельзя вынести в модель.  
То есть, контроллер должен содержать в себе только логику, которая связывает между собой модели и представления. Это и называется "тонким контроллером".

Определение выигрыша и проигрыша это та логика, которая не зависит от представления и является общей для программы в любой среде: консоль, андроид etc.  
Следовательно, это логика модели. А кто у нас тут модель? Правильно- класс Раунд.

### Пакет console

От пакета с таким названием мы классы, которые занимаются только вводом данных от юзеры через консоль и распечатки данных для юзера в консоль.  
Такие классы не должны содержать сложную логику, например какую-либо логику игрового процесса типа определения выигрыша, проигрыша etc.  
В принципе, классы в этом пакете соответствуют этим требованиям.

**9. class InputHandler + class InputValidator + class InputParser**

Идея классов понятна, но они сделаны чисто в процедурном стиле.

Например, валидатор содержит в себе валидирование цифр и русских букв.  
И выбор конкретного вида валидации происходит через сложную систему "типов":
```java
public class InputValidator {

  public boolean isValid(String value, InputType type) {...}

  private boolean isNumber(String value) {...}

  private boolean isLetter(String value) {
    //...
    return Character.UnicodeBlock.of(value.charAt(0)) == Character.UnicodeBlock.CYRILLIC;
  }
}
```

Этот класс нарушает SRP и OCP.  
Что случится, если понадобится валидация строки? Придется вносить изменение в класс.   
Что случится, если понадобится валидация не только русской буквы, а еще монгольской? Придется вносить изменение в класс.  
Это чисто процедурный подход.

ООП подход выглядит примерно так.  
Создаем некий абстрактный валидатор:
```java
public interface Validator<T> {
  boolean isValid(T value);
}
```

Дальше делаем нужные нам валидаторы. Каждый валидатор валидирует что-то одно:
```java
public class RusLetterValidator implements Validator<Character> {
  @Переопределить
  public boolean isValid(Character value) {
     //true если value это буква русского алфавита
  }
}

public class IntegerMinMaxValidator implements Validator<Integer> {
  //....  

  public IntegerMinMaxValidator(int min, int max) {...}

  @Переопределить
  public boolean isValid(int value) {
     //true если value находится внутри min-max
  }
}
```

В таком же процедурном стиле сделан `class InputHandler`
```java
public class InputHandler {
  public <T> T getInput(String text, InputType type) {...}
}
```

### Пакет core

От пакета с названием core мы ждём самую важную бизнес-логику и основные строительные блоки приложения, 
которые не зависят от внешних фреймворков, баз данных, пользовательского интерфейса или деталей ввода-вывода.

Здесь же находятся классы с названием "контроллер", а контроллеры это точно не кор. 

Поэтому название пакета неправильное.

Контроллеры знают всё про слои view и модель.  
Задача контроллеров состоит в том, чтобы связывать модели и вью в единую программу.  
Контроллер должен быть тонким.


**11. class GameController**

+ 👍 Идея разделения игры на модель-движок и её контроллер это хорошо. Но нужно правильно разнести методы по этим классам.

- Нейминг.

Класс называется Game-контроллер, но контролирует он не `Game`, а `Round`.  
Приведи названия  к общему стандарту. Либо классы `Game` и `GameController`, либо `Round` и `RoundController`.  
Лично мне больше нравится `Game` + `GameController`.

- Нарушение DI.

Сейчас конструктор ничего в себя не принимает и поэтому программа негибкая.   
Как следствие- нельзя сделать разные Main-классы с разными игровыми конфигурациями. 

Если этот класс Game-контроллер, то он должен в себя принимать `Game`.  Например, так:
```java
class GameController {
  private final Game game;

  public GameController(Game game) {...}    
  //...
}
```

Это даст гибкость- можно будет не меняя код в классах, делать разные игровые конфигурации в Майнах.  
Например:
```java
public class FirstMain {

  //Тестовая конфигурация: один игровой раунд с жестко прописанным словом для тестирования  
  public static void main(String[] args) {
    Game game = new Game("Тест");
    GameController controller = new GameController(game);
    controller.start();
  }
}

public class SecondMain {

  //Вторая конфигурация: один игровой раунд с рандомным словом из файла  
  public static void main(String[] args) {
    FileDictionary dictionary = new FileDictionary("words.txt");
    String word =  dictionary.getRandom();
    Game game = new Game(word);

    GameController controller = new GameController(game);
    controller.start();
  }
}
```

Ну и конфиг с меню "Играть или выйти" примерно такой:
```java
public class ThirdMain {

  //Третья конфигурация: игра через диалог "играть или выйти"  
  public static void main(String[] args) {
    FileDictionary dictionary = new FileDictionary("words.txt");

    //Создание объекта через паттерн билдер
    Menu menu = Menu.addTitle("Добро пожаловать в консольную игру 'Виселица'!")
                  .addItem("Новая игра", () -> start(dictionary)) 
                  .addItem("Выход", () -> System.exit(0)) 
                  .build();

    while(true) {
      menu.show();  //распечатать меню
      menu.execute();  //выполнить пункт меню   
    }
  }

  private static void start(FileDictionary dictionary) {
    String word =  dictionary.getRandom();
    Game game = new Game(word);

    GameController controller = new GameController(game);
    controller.start();
  }
}
```

## ВЫВОД

Несмотря на то, что в проекте несколько классов, он написан в смешанном ООП/процедурном стиле.  
Программа в ООП стиле должна быть декомпозирована по правилам ООП и использовать ООП подход для реализации типичных задач.  
Здесь не видно ООП декомпозиции.

**Признаки ООП:**

🔹 Программа разделена на классы, некоторые из которых описывают какую-то отдельную понятную сущность: принтер, загрузчик слов(словарь) etc.  
🔹 Отдельный класс с точкой входа main, который тут используется правильно- ведет диалог "играть или выйти" и запускает игру.

**Признаки процедурного стиля:**

🔸 Не выявлены и не сделаны в виде классов менее очевидные, чем Словарь, сущности. Например, Секретное слово.  
Значит нет системного понимания объектно-ориентированной декомпозиции.  

🔸 Процедурные подходы при создании классов. Например, валидатор.  
🔸 Не используется Dependency Injection- классы не принимают в конструктор необходимые зависимости и поэтому негибкие. Например, игровой контроллер.

Осознанно используй такие названия, как `core`, `model`, `view`, `controller`, `service` etc.  
Проверяй, какие требования эти названия предъявляют к классам.
