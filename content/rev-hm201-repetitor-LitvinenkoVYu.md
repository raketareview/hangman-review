**2. Каждый класс должен находиться в отдельном .java файле**

Сейчас в одном файле Main.java находится два равноценных класса.  
В одном .java файле одновременно могут находиться несколько классов только в одном случае - когда один из классов является внутренним классом другого.  
Условный пример:
```java
public class First {
  //...

  public class Second {
    //...
  }    
}
```

**2. Нарушение инкапсуляции**

Хотя инкапсуляция это термин ООП, но даже при процедурном стиле в java используются классы.  
Поэтому в классе Main все поля и методы, кроме `main()` должны быть private.

**3. Форматирование**

- Форматирование строк.

используй форматирование - тогда сразу будет виден весь шаблон сообщения

- Комментарий противоречит коду. Не вижу предотвращения
```java
class HangmanPicture {
  public HangmanPicture() {
  }   // предотвращение создание объекта извне

  //...
```

Если имеется в виду это
```java
private HangmanPicture() {
}   // предотвращение создание объекта извне
```
то нам не нужно объяснять очевидные вещи - мы понимаем, зачем нужны приватные конструкторы.

- Комментарий объясняет плохой код
```java
while (!isGameWon(mask) && !isGameLost(errors)) { // вызов true, если игра закончена
```

Здесь комментарий призван объяснять сложный код. Ну или код, который показался сложным.  
Вместо комментария нужно сделать так, чтобы код сам себя объяснял:
```java
while (!isGameOver(...))) {...}

private static boolean private boolean isGameOver(...) {
  return isGameLost(...) || isGameWon(...);
}
```

Когда в проекте много каментов, это плохо - пользы от них практически нет, они только забивают пространство и мешают читать код.  
В идеале кроме `TODO` комментариев вообще не должно быть. 
Код должен объяснять сам себя через правильный нейминг и лаконичный код.

```java
  //...
  return words.get(index);  <-- Если сработает return, то инструкция else никогда не выполнится
```

**10. Большой божественный метод** 

Из-за своей запутанности и большого размера, метод `playRound()` трудно читаем.

Если какой-то метод получается ощутимо длинным, то есть больше 20-30 строк, то скорее всего, он делает много разных дел одновременно.  
Такой метод нужно сокращать: выявить в нём отдельные смысловые блоки и вынести их во вспомогательные методы.

Например, смотрим на божественный метод и находим в нём отдельные смысловые блоки
```java
public static int playRound(String secretWord, int errors, char[] mask, ArrayList<

  System.out.print("Введите букву: ");
  String input = sc.next();
  input = input.toLowerCase();
  if (input.length() > 1) {
    System.out.println("Неверный ввод, вводи по одной букве!");
    continue;
  }
  char letter = input.charAt(0);
   
  //ещё куча кода
}
```

Что делает этот кусок кода? Он от юзера получает букву.  
Выносим этот код во вспомогательный метод:
```java
public static int playRound(String secretWord, int errors, char[] mask, ArrayList<
  //куча кода
  char letter = inputLetter();
  
  //ещё куча кода
}

    // иначе пишем сообщение о неправильном вводе 
  }    
}
```

**11. Использование глобальных переменных при процедурном стиле программирования**

Сейчас класс не содержит изменяемых полей, а содержит только константы.

Но программе иногда кроме констант нужны еще и изменяемые данные.
Причем эти данные нужны не локально, не только в рамках одного метода.
А для разных частей алгоритма игры, то есть, для многих методов сразу.

Например: отгадываемое слово и его маска, перечень использованных букв, счетчик ошибок и прочее.

Сейчас в рамках класса нет таких "глобальных полей".
Эти данные сейчас сделаны переменными методов и они перекидываются из метода в метод через входящие аргументы.

Это приводит к тому, что сигнатура таких методов сильно разбухает - приходится принимать во входящие кучу "общих" данных
```java
public static int playRound(String secretWord, int errors, char[] mask, ArrayList<Character> usedLetters, Scanner sc) {...}
public static boolean processGuess(char letter, String secretWord, char[] mask) {...}
```
Код становится более сложным и хуже читаем по сравнению с тем, если бы данные принимались не в аргументы метода, а брались из окружения класса.

Условный пример:
```java
//❌️ ПЛОХО:
private void openLetter(String word, char[] mask, char letter) {
  //открывает букву letter в маске,
  //если эта буква присутствует в слове
}

//✅ ХОРОШО:
private static String word;
private static char[] mask;

private void openLetter(char letter) {
  //открывает букву letter в маске,
  //если эта буква присутствует в слове
}
```

В таком виде поля `word` и `mask` фактически становятся глобальными переменными - стандартная ситуация при процедурном программировании.

Отказ от использования глобальных переменных при процедурном стиле программирования провоцирует написание божественных методов.
Потому что в этом случае не хочется писать методы, которые кидают друг целую кучу аргументов во входящие.

Вопрос о том, какие переменные должны быть полями класса, а какие - полями методов, всегда нужно решать индивидуально.  
Но если ты видишь, что несколько методов перекидывают друг другу одни и те же поля, то возможно эти поля стоит сделать полями класса.

```java
public static boolean processGuess(char letter, String secretWord, char[] mask) {
  boolean isGuessed = false;
  for (int i = 0; i < secretWord.length(); i++) {
    if (secretWord.charAt(i) == letter) {
      mask[i] = letter;  <-- ВЫПОЛНЕНИЕ КОМАНДЫ
```
