**1. Нейминг**

- Не используй в названиях методов слово "try".

"try" это зарезервированное слово, оставь его для try-catch
```java
boolean trySetRevealedLetters(int revealedLetters)
```

Метод не должен "пытаться", он должен делать.
Если метод по какой-то причине не может выполнить свой контракт, он должен кинуть исключение.

- Буквы это НЕ СТРОКИ. 

Потому что строка может состоять из любого количества символов, от нуля включительно.  
А буква это всегда только один символ.  
Поэтому не используй для них тип `String`, они должны быть `char`
```java
String letter

//ПРАВИЛЬНО:
char letter
```

- В `ConsoleUI` для разных концепций используются похожие по смыслу названия, которые можно спутать друг с другом: `print` и `show`. 

- Название обманывает. 

Метод не читает набор (set) меню раскрытых букв: 
```java
public int readSetRevealedLettersMenu() {
  System.out.print("Ввод: ");
  return readNumber();
}
```
Название должно соответствовать тому, что делает метод.

- Не называй переменные префиксом "new".

Во-первых, "new" это зарезервированное слово.  
Во-вторых, все переменные при их создании являются новыми.

Придумывай альтернативные названия, которые объяснят суть таких переменных
```java
int newValue = consoleUI.readSetRevealedLettersMenu();

//ПРАВИЛЬНО:
int revealedLettersCount = consoleUI.readSetRevealedLettersMenu();
```

- Название обманывает. Список хранит не только открытые буквы, но и закрытые тоже
```java
public class HangmanGame {
  private String word;
  private final List<String> revealedLetters;
  //...
}

//ПРАВИЛЬНО:
public class HangmanGame {
  private String word;
  private final List<String> mask;
  //...
}
```

**4. Комментарии**

Комментарии здесь в основном не несут полезной нагрузки, а констатируют очевидное
```java
/*метод show последовательно вызывает методы print и read
 *дальше есть чёткое разделение методов
 *print - вывод информации
 *read - получение данных от пользователя
 *show - логическое объединение, где есть как вывод информации, так и получение данных
 */
```

Если метод последовательно вызывает другие методы - я это увижу.  
Объяснять в комментариях нужно сложную неочевидную логику, последовательный вызов методов к ней не относится.

Названия "print", "read" - слишком очевидные, их пояснять не надо.

Объяснение отличия "show" от "print" в виде комментария здесь полезно.  
Но полезно оно только потому, что выбрано неудачное название "show", которое выглядит как синоним принта.

Show-методы нужно убрать - они совмещают две разные операции. 

Когда в проекте много каментов, это плохо - пользы от них практически нет, они только забивают пространство и мешают читать код.  
В идеале кроме `TODO` комментариев вообще не должно быть. 
Код должен объяснять сам себя через правильный нейминг и лаконичный код.

**5. Exceptions**

- Текст в Exception всегда должен быть на английском языке.
```java
throw new IllegalStateException("словарь пуст"); <-- Неправильно: сообщение в исключении не на английском языке
```
Исключение - это не просто телеграмма, которая летит сквозь слои.

У exception особое назначение - если исключение вылетит и не будет перехвачено внутри программы, то аварийно прекратит выполнение программы.  
Тогда на экране будет распечатано сообщение эксепшена, и это сообщение должно быть понятно сисадмину в любой точке планеты.  
А значит, сообщение должно быть на английском.

Интерпретация исключения и перевод его на локальный язык должны происходить там, где это соответствует архитектуре программы.  
Или не происходить вовсе, если исключение не планируется перехватывать.

+ 👍 Правильно перехватил непроверяемое исключение и вместо него кинул исключение ПРАВИЛЬНОГО для этого случая типа
```java
catch (IOException e) {
  throw new UncheckedIOException(..., e);
}
```

- Нарушение SRP.

Если это конфиг, то он должен просто хранить данные.  
Заполнять данными сам себя он не должен.

Раздели логику:  
Конфиг должен только хранить данные.  
Другой класс, например, простая фабрика, должен создавать экземпляр конфига.

- Не усложняй проекты сверх ТЗ.

Использование конфига усложняет проект и, при недостаточном умении, размывает архитектуру и делает её более громоздкой и запутанной.
Здесь произошло именно так.

Приоритет состоит в том, чтобы научиться писать хорошую архитектуру, а не придумывать себе лишние заботы.  
При написании учебных проектов соблюдай принцип YAGNI.  

Поэтому лучшим решение здесь будет просто убрать из проекта конфиги и всю работу с ними.

- Разделяй команды и запросы. 

Этот метод совмещает команду и запрос.  
Команда: произвести некие действия.  
Запрос: сказать, были ли выполнены действия
```java
public boolean trySetRevealedLetters(int revealedLetters) {
  if (revealedLetters >= 0 && revealedLetters < 3) {
    this.revealedLetters = revealedLetters;  <-- Изменение состояния объекта: выполнение команды
    return true;  <-- Выполнение запроса
  }
  return false;  <-- Выполнение запроса
}
```
Метод должен или выполнять команду, или отвечать на запрос.

В проекте есть огромный метод

Алгоритм работы этого метода понять невозможно. Но судя по названию, он должен в начале игры открыть заданное количество букв в слове.

Если я правильно понимаю из названия этого метода его назначение, то сейчас сложность и объем кода этого метода не соответствует поставленной задаче. 

Я бы разбил задачу на две части.

Сначала я бы придумал, как открыть в маске любую букву слова:
```java
private String word;  //"привет"
private char[] mask;  //"------"

public void openLetter(char letter) {  //или revealLetter(...)
  boolean found = false;
  for(int n = 0; n < word.length(); n++) {
    if(word.charAt(n) == letter) {
      mask[n] = letter;
      found = true;
    }
  }

  if(!found) {
    throw new IllegalArgumentException(...); // попытались открыть отсутствующую в слове букву - так нельзя
  }
}
```

Метод открытия буквы нужен в алгоритме игры в целом, а не только для начального открытия нескольких букв.

Теперь придумаем, как открыть заданное количество РАЗНЫХ букв.

Просто открывать их по случайным индексам в слове нельзя. Потому что на случайных индексах может находиться одна и та же буква: "пАрАболА".

Значит, нужно взять все уникальные буквы в слове, перемешать их и открыть заданное количество этих букв:
```java
public void openRandomLetters(int count) {
  Set<Character> uniqueLetters = new HashSet<>();
  for(char letter : word.toCharArray()) {
    uniqueLetters.add(letter);  //в сет не попадут одинаковые буквы
  }

  List<Character> letters = new ArrayList<>(uniqueLetters);  // сет перемешивать нельзя, поэтому сливаем его в список
  Collections.shuffle(letters);  // перемешали буквы

  for(int i = 0; i < count; i++) {
    openLetter(letters.get(i));
  }
}
```
Допущения: метод вызывается только в начале игры, когда все буквы закрыты; count меньше количества уникальных букв в слове.

Это не единственный простой алгоритм открытия случайных букв в слове, можешь придумать альтернативный.

## ВЫВОД

Эта реализация имеет признаки и процедурного, и объектно-ориентированного стилей.

Признаки ООП:  
🔹 Программа разделена на классы, каждый из которых описывает отдельную сущность: общая игровая логика, словарь и т.д.  

Признаки процедурного стиля:  
🔸 Не выявлены и не сделаны в виде классов менее очевидные, чем "Словарь", сущности. Например, "Секретное слово".  
Значит, нет системного понимания объектно-ориентированной декомпозиции.

🔸 Те классы, на которые сейчас поделена программа, могут быть и в процедурной программе - процедурный стиль сам по себе не отрицает возможность создания нескольких классов.  
🔸 Процедурные приёмы при решении задач: меню, пользовательский ввод.

Код часто сложный и непонятный.  
Чтобы сконцентрироваться на написании хорошей архитектуры, убери из программы всё лишнее: конфиги и сложное меню.  
Меню сделай простым, с двумя опциями: "играть или выйти".

Сейчас все эти усложнения ничего хорошего для архитектуры не дают, а только размывают её.
