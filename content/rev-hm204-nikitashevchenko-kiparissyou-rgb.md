## ЗАМЕЧАНИЯ

**1. Нейминг**

- Однобуквенные переменные.

Однобуквенные переменные в большинстве случаев допустимы только в циклах для обозначения счетчика циклов, либо в цикле `foreach` для присвоения переменной текущей итерации
```java
boolean checkDouble(String a, Set b)

//ПРАВИЛЬНО:
boolean checkDouble(String первоеОсмысленноеНазвание, Set второеОсмысленноеНазвание)
```
Возможно, ты однобуквенные названия используешь по аналогии с уроками геометрии, где стороны треугольника обозначались буквами a, b, c.
Но в программировании всё не так - здесь название переменной должно объяснять, что хранит эта переменная.

- Название метода должно объяснять, что делает метод. Из названия "проверь дважды" (проверь дубль?) я ничего понять не могу
```java
boolean checkDouble(String a, Set b)
```

- Предлог "To" используй только в методах конвертации из одного в другое. 

Предлог "To" используется в методах конвертации: `toList()`, `toString()`, `toInt()`, `meterToFeet()`.   
В остальных случаях воздерживайся от этого. Иначе сейчас кажется, что метод конвертирует ход в астерикс
```java
String turnToAsterisks(StringBuilder a)
```

- Название должно объяснять, что делает метод. Этот метод не конвертирует ход в астерикс, он создает маску слова
```java
public static String turnToAsterisks(StringBuilder a) {
  String stars = "";
  for (int i = 0; i < a.length(); i++) {
    stars = stars + "*";
  }
  return stars;
}

//ПРАВИЛЬНО:
public static String createMask(StringBuilder word)
```

- Не называй поля "переменная1", "переменная2", это совсем плохой тон. Всегда можно найти более осмысленные названия
```java
StringBuilder stars1 = new StringBuilder(stars);
```

- Этот метод возвращает не строку, а стрингбилдер
```java
StringBuilder getStringFromVocab() {
  // возвращает случайное слово из словаря
}

//ПРАВИЛЬНО:
String getRandomWord() {
  // возвращает случайное слово из словаря
}
```

- Ненужное уточнение.

Если бы в проекте кроме слова в игре было ещё слово вне игры, тогда уточнение имело бы смысл. Сейчас - не имеет
```java
String wordInGame

//ПРАВИЛЬНО:
String word
```

- В названия не нужно вставлять частицы "Of", "The", "Are" и т.д.

Это только делает названия более громоздкими.  
"Of" в названиях методов можно использовать только в контексте "valueOf()"
```java
int countOfMistakes = 0;

//ПРАВИЛЬНО:
int mistakeCount = 0;
```

- Какой-то ад перечислений
```java
List<StringBuilder> wordInGameAndMask = List.of(mask, wordInGame);
```
Сформулируй, что такое сущность "слово + его маска".  
Условный пример: "четыре латы, полосатый хвост, два уха" vs "кот".

В данном случае это просто результат работы метода
```java
public static List<StringBuilder> gameProcess() {
  //...
  List<StringBuilder> wordInGameAndMask = List.of(mask, wordInGame);

  return wordInGameAndMask;
}

//ПРАВИЛЬНО:
public static List<StringBuilder> gameProcess() {
  //...
  return List.of(mask, wordInGame);
}
```

Но если нужно вводить поясняющую переменную, тогда так:
```java
public static List<StringBuilder> gameProcess() {
  //...
  List<StringBuilder> result = List.of(mask, wordInGame);
  return result;
}
```

- Придерживайся единообразия. 

Много методов с одинаковым префиксом "check", которые ведут себя по-разному
```java 
boolean checkDouble(String a, Set b) - Возвращает результат какой-то проверки
StringBuilder checkUserLetter(String a, StringBuilder fromVocab, StringBuilder stars) - Создает внутри себя какой-то стрингбилдер и возвращает его
void checkVictory(List<StringBuilder> a) - Ничего не возвращает, печатает результаты игры
```

Сформулируй для себя единый контракт check-методов и придерживайся его при наименовании методов.  
Не нужно использовать общий префикс для методов, которые выполняют принципиально разные операции.

- Название обманывает. 

От метода "проверить победу" мы ожидаем проверки победы.  
А на самом деле этот метод печатает результаты игры
```java
void checkVictory(List<StringBuilder> a) {
  // печатает результаты игры
}

//ПРАВИЛЬНО:
void printGameResult(List<StringBuilder> a) {...}
```

В этой реализации вообще характерно, что названия не объясняют того, что делает метод. Либо объясняют неправильно.  
Например, метод `StringBuilder checkUserLetter(...)` не проверяет букву юзера, а открывает букву в маске.

- Название метода должно быть глаголом. Это название - существительное
```java
List<StringBuilder> gameProcess() 
```

- Не используй зарезервированные слова, в том числе "new", в качестве префиксов названий методов. К тому же "новая игра" - это не глагол
```java
void newGame()
```

- Название обманывает, нарушение контракта. Результатом работы этого метода может быть либо запуск новой игры, либо окончание работы программы
```java
void newGame()
```

- Венгерская нотация.

В названии переменных не пиши тип данных, к которым они относятся.  
И вообще не употребляй венгерскую нотацию. 
Название переменной должно отвечать на вопрос что хранит переменная, а не как хранит
```java
String userString = scanner.nextLine().toLowerCase().trim();

//ПРАВИЛЬНО:
String text = scanner.nextLine().toLowerCase().trim();
```

- Компилируй регулярные выражения.

Компиляция регулярного выражения в объект `Pattern` с помощью `Pattern.compile()` позволяет повысить производительность при многократном использовании

```java
//ПРАВИЛЬНО:
private static final String REGEX = "[А-Яа-яЁё]+";
private static final Pattern PATTERN = Pattern.compile(REGEX);

//...
String text = scanner.nextLine().toLowerCase().trim();
Matcher matcher = PATTERN.matcher(text);

if (text.length() == 1 && matcher.matches()) {...}
```

**11. Используй StringBuilder**

Плюсование строк в цикле это расточительно - при конкатенации пересоздаются объекты типа String.  
Для складывания строк в цикле применяй StringBuilder - это с точки зрения ресурсов более оптимальный процесс.  

Посмотри, Idea подчеркивает здесь плюсование желтым цветом, это она предлагает заменить складывание строк использованием стрингбилдера.  
Поставь курсор на желтое подчеркивание, слева появится желтая лампочка, клацни на нее, выбери пункт "Convert..." и идея автоматически заменит плюсование на StringBuilder
```java
public static String turnToAsterisks(StringBuilder a) {
  String stars = "";
  for (int i = 0; i < a.length(); i++) {
    stars = stars + "*";
  }
  return stars;
}

//ПРАВИЛЬНО:
public static String turnToAsterisks(StringBuilder a) {
  StringBuilder stars = new StringBuilder();
  for (int i = 0; i < a.length(); i++) {
    stars.append("*");
  }
  return stars.toString();
}
```

Конкретно здесь можно сделать ещё проще:
```java
public static String turnToAsterisks(StringBuilder a) {
  int count = a.length();
  return "*".repeat(count);
}
```

**14. Использование глобальных переменных при процедурном стиле программирования**

Сейчас класс не содержит изменяемых полей, а содержит только константы.

Но программе иногда кроме констант нужны еще и изменяемые данные.
Причем эти данные нужны не локально, не только в рамках одного метода.
А для разных частей алгоритма игры, то есть, для многих методов сразу.

Например: отгадываемое слово и его маска, перечень использованных букв, счетчик ошибок и прочее.

Сейчас в рамках класса нет таких "глобальных" полей.
Эти данные сейчас сделаны переменными методов и они перекидываются из метода в метод через входящие аргументы.

Это приводит к тому, что сигнатура таких методов сильно разбухает - приходится принимать во входящие кучу "общих" данных
```java
public static StringBuilder checkUserLetter(String a, StringBuilder fromVocab, StringBuilder stars) {...}
public static boolean checkDouble(String a, Set b) {...}
```
Код становится более сложным и хуже читаемым по сравнению с тем, если бы данные принимались не в аргументы метода, а брались из окружения класса.

Условный пример:
```java
//❌️ ПЛОХО:
private void openLetter(String word, char[] mask, char letter) {
  //открывает букву letter в маске,
  //если эта буква присутствует в слове
}

//✅ ХОРОШО:
private static String word;
private static char[] mask;

private void openLetter(char letter) {
  //открывает букву (letter) в маске (mask),
  //если эта буква присутствует в слове (word)
}
```

Здесь поля `word` и `mask` фактически становятся глобальными переменными - стандартная ситуация при процедурном программировании.

Отказ от использования глобальных переменных при процедурном стиле программирования провоцирует написание божественных методов.
Потому что в этом случае не хочется писать маленькие методы, которые кидают друг другу целую кучу аргументов во входящие. А хочется делать большие методы.

Вопрос о том, какие переменные должны быть полями класса, а какие - полями методов, всегда нужно решать индивидуально.  
Но если ты видишь, что несколько методов перекидывают друг другу одни и те же поля, то возможно эти поля стоит сделать полями класса.

**15. Создавай вспомогательные методы, делай программу более простой и понятной**

```java
//ПРАВИЛЬНО:

//...

//..

}

private static boolean isLose() {
  return mistakeCount >= MAX_MISTAKE; 
}
```
Даже если метод состоит из одной строки, но при этом делает код программы читабельнее, то этот метод имеет право на жизнь.

**16. Не делай адских условий в if**

Этот адский ад вообще не читается
```java
if (mask.toString().equals(checkUserLetter(letter, wordInGame, mask).toString())) {...}
```

И я не драматизирую, этот код реально невозможно понять.  
Здесь в одну строку склеено много инструкций (четыре, пять?) + название метода, которое ничего не объясняет: `checkUserLetter()`.

Приоритет должен состоять в написании простого и понятного кода, а не в экономии строчек.  
Используй вспомогательные методы или поясняющие переменные.

**17. Рефакторинг**

Рассмотрим рефакторинг этой программы на примере одного из типичных методов
```java
public static boolean checkDouble(String a, Set b) {
  boolean hasLetter = false;

  if (b.contains(a)) {
    hasLetter = true;
  } else {
    b.add(a);
  }
  return hasLetter;
}
```

Для начала нужно всем переменным и методам дать нормальные имена, которые соответствуют конвенции наименований Oracle Java и хорошим практикам.  

Если смотреть на этот метод отдельно, то вообще не понятно, что это такое.  
Нужно рассмотреть этот метод в контексте его использования:
```java
boolean letterIsUsed = checkDouble(letter, usedLetters);
```
Ага. Предполагаю, что этот метод проверяет, что `String a` это буква, а `Set b` это сет использованных букв.  
А задача метода - проверить, входит ли буква в сет использованных букв.  

Даю нормальные имена:
```java
public static boolean isUsedLetter(String letter, Set<String> usedLetters) {
  boolean hasLetter = false;

  if (usedLetters.contains(letter)) {
    hasLetter = true;
  } else {
    usedLetters.add(letter);
  }
  return hasLetter;
}
```

Теперь даже без контекста использования понятно, что делает этот метод и зачем он нужен.

Сразу возникает вопрос: а почему буквы здесь это строки?  
Буква - это ВСЕГДА одиночный символ, а строка это текст произвольной длины от нуля символов и более.

Переделываем:
```java
private static boolean isUsedLetter(char letter, Set<Character> usedLetters) {
  if(usedLetters.contains(letter)) {
    return true;
  }
  
  usedLetters.add(letter);
  return false;
}
```

Видно, что метод нарушает правило разделения команд и запросов.  
А также нарушает правило одной операции - метод делает два разных дела: проверяет букву и добавляет её в список использованных.  

Делаем два разных метода:  
```java
private static boolean isUsedLetter(char letter,  Set<Character> usedLetters) {
  return usedLetters.contains(letter)
}

private static void addUsedLetter(char letter,  Set<Character> usedLetters) {
  usedLetters.add(letter);
  //опционально: кинуть исключение если попытались повторно добавить одну и ту же букву
}
```

Список юзаных букв нужен многим методам - в соответствии с духом процедурного программирования делаем его глобальной переменной:
```java
private static Set<Character> usedLetters;

private static boolean isUsedLetter(char letter) {
  return usedLetters.contains(letter)
}

private static void addUsedLetter(char letter) {
  usedLetters.add(letter);
}
```

Контекст использования:
```java
while(!isGameOver()) {
  //...  
  char letter = inputLetter();

  if(isUsedLetter(letter)) {
    // буква уже была введена ранее - напечатать сообщение 
    continue;   
  } 

  addUsedLetter(letter);  
  //...
}
```
