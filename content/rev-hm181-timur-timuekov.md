**2. Исключения**

- Текст в Exception всегда должен быть на английском языке.
```java
throw new RuntimeException("Не удалось прочитать словарь слов", e);
```
Исключение это не просто телеграмма, которая летит сквозь слои.

У exception особое назначение- если исключение вылетит и не будет перехвачено внутри программы, то аварийно прекратит выполнение программы.  
Тогда на экране будет распечатано сообщение эксепшена, и это сообщение должно быть понятно сисадмину в любой точке планеты.  
А значит, сообщение должно быть на английском.

Интерпретация исключения и перевод его на локальный язык должны происходить там, где это соответствует архитектуре программы.  
Или не происходить вовсе, если исключение не планируется перехватывать.

- Не бросай базовый эксепшен. Конкретизируй ситуацию- бросай то исключение, которое подходит под этот конкретный случай
```java
try (...) {
  //...
} catch (IOException e) {
  throw new RuntimeException("Не удалось прочитать словарь слов", e);
}
```

**3. Нарушение DRY**

- Магические буквы, числа, слова. Вводи константы 
```java
System.out.println("1 — Новая игра, 2 — выход");
if (input != 1 && input != 2) {...}
if (input == 2) {...}

//ПРАВИЛЬНО:
private static final int START = 1;
private static final int QUIT = 2;

System.out.printf("%d — Новая игра, %d — выход  \n", START, QUIT);
if (input != START && input != QUIT) {...}
if (input == QUIT) {...}
```

- Общая магия.

Если к одной и той же магической штуке обращаются два разных класса, то делай ее константой в одном из этих двух классов.  
Либо перенеси ее в третий класс и из первых двух классов обращайся к этим константам- эти данные должны быть синхронизированы между собой
```java
public class Main {
  public static void main(String[] args) {
    //...
    System.out.println("Ошибок: " + session.getMistakesCount() + " из 6");
  }
}

public class GameSession {

  //...
  public boolean isGameOver() {
    return isWon() || wrongLetters.size() >= 6;
  }
}
```

**5. class WordDictionary**

- Путь к файлу класс должен получать в конструктор. 

Иначе класс становится не универсальным.  
Допустим, в программе будет несколько разных текстовых файлов- на разных языках или по разным темам.  
Тогда вместо нескольких специализированных классов Словаря, где имя файла словаря будет жестко прописано в каждом из классов, 
можно будет использовать один универсальный класс Словарь.

- Минимальный размер слов для загрузки в словарь.

Из файла читаются только слова, которые содержат больше определенного количества букв
```java
if (line.length() >= 5)  {...}
```
Словарь не должен самостоятельно принимать решение, слова какого размера нужно загружать, а какого размера нет.  
Минимальный размер слова класс должен принимать в конструктор так же, как путь к файлу. 

- Реакция на ошибки при чтении файла.

В проекте предусмотрено, что может возникнуть исключение при чтении файла со словами.  
В этом случае просто перехватывает проверяемое исключение и вместо него кидает непроверяемое
```java
try (BufferedReader reader = new BufferedReader(new InputStreamReader(inputStream, StandardCharsets.UTF_8))) {
  //читает файл
} catch (IOException e) {
  throw new RuntimeException("Не удалось прочитать словарь слов", e);  <-- бросает непроверяемое исключение вместо проверяемого
}
```
В данном случае такой способ реагирования на ошибку неправилен. 
Потому что если файл действительно будет отсутствовать, то программа аварийно прекратит свою работу. 
И напишет в консоль непонятные для пользователя сообщения
```java
C:\Users\alex\.jdks\liberica-full-26.0.2\bin\java.exe "-javaagent:C:\Prog\IntelliJ IDEA 2026.1\lib\idea_rt.jar=3430" -Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -classpath C:\MyReviews\PROG\Hm-timur-\hangman-java-master\target\classes hangman.Main
Exception in thread "main" java.lang.NullPointerException
	at java.base/java.io.Reader.<init>(Reader.java:289)
```
Здесь должна быть другая реакция на отсутствие файла со словами.  
Нужно сказать юзеру, что файл со словами по указанному пути открыть не удалось и поэтому работа программы будет завершена.  
И завершить работу программы не аварийно, через exception, а корректно- например, через return.

**7. class GameSession**

+ 👍 Что-то типа движка. Движок это хорошо.

Движок это вся игровая логика без взаимодействия с представлением.  
Игровая логика с взаимодействием с представлением в таких случаях выносится в отдельный контроллер.  
Здесь движок это `GameSession`, а роль контроллера выполняет `Main`.

- Побочный эффект. 

Судя по названию, метод должен проверять (типизированную?) букву, что бы это ни значило.
Но кроме этого метод неявно, то есть без указаний на то в своем названии, вносит изменение в состояние класса- заносит букву в список правильных или неправильных. 
```java

```
Метод нужно разделить на несколько, каждый из которых будет выполнять только одну задачу.

**8. class Main**

Содержит точку входа `main`.

- Нарушение SRP.

Main должен только сконфигурировать зависимости и запустить программу.  
Управлять работой программы этот класс не должен.  
В Main'e возможен только диалог "Играть или выйти"- это все еще относится к ответственности конструирования и запуска системы.

*Мартин, "ЧК", гл.11, "Отделение конструирования системы от ее использования"*

- Класс нужно разделить на два.

Логику создания и запуска игры через диалог "Играть или выйти" нужно оставить в Main.  
Управление движком игры нужно вынести в класс-контроллер.  

Контроллер игры должен содержать в себе ту часть игровой логики, которая зависит от представления.  
То есть, когда нужно получить от юзера букву, дёрнуть движок, распечатать результаты хода.

- Большой метод `main()` на 40 строк.

Методы должны делать одно дело на одном уровне абстракции.  
Например, в `main` выполняется действие на более низком уровне абстракции, чем остальные:
```java
public static void main(String[] args) {
  //много кода

  int input = scanner.nextInt();

  scanner.nextLine();

  if (input != 1 && input != 2) {
    System.out.println("Неверный ввод!");
    continue;
  }
 if (input == 2) {
   System.out.println("Игра завершена.");
   break;
 }

  //много кода
}

//ПРАВИЛЬНО:
public static void main(String[] args) {
  //много кода
  int command = inputCommand();

  //много кода
}

private static int inputCommand() {
  System.out.printf("%d — Новая игра, %d — выход  \n", START, STOP);    
  while(true) {
   int command = scanner.nextInt();
   //вернуть command если он равен START или STOP
  }
}

```

## АРХИТЕКТУРА

Программа содержит признаки и объектно-ориентированного и процедурного стилей.

Признаки ООП:  
🔹 Программа разделена на классы, каждый из которых описывает отдельную сущность: хранилище картинок, словарь, движок игры.  

Признаки процедурного стиля:  
🔸 Не выявлены и не сделаны в виде классов менее очевидные, чем Словарь, сущности. Например, Секретное слово. 
Значит нет системного понимания объектно-ориентированной декомпозиции.

🔸 Класс Main совмещает в себе конструирование системы и её использование.

Скорее это всё же процедурный стиль- не видно системного понимания правил ООП декомпозиции.

Методы в основном сделаны хорошо.

Большая их часть соответствует базовым требованиям:  
🔹 Маленький размер  
🔹 Выполняют одну операцию на одном уровне абстракции  
🔹 Не совмещают команду и запрос  
🔹 Не содержат больше трех уровней вложенности
🔹 Не имеют побочных эффектов

Но есть методы, которые этому не соответствуют: `main()`, `checkTypedLetter(...)`.
