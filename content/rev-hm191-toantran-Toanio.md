**2. Exceptions**

- Не бросай базовый exception. Конкретизируй ситуацию- бросай то исключение, которое подходит под этот конкретный случай
```java
throw new RuntimeException("Ошибка чтения файла", e);
```
*Хорстманн "Java. Библиотека профессионала", т.1, гл.11*
```java
"Не ограничивайтесь генерацией RuntimeException. 
Найдите подходящий подкласс или создайте собственный." - Хорстманн
```

- Текст в Exception всегда должен быть на английском языке.
```java
throw new FileNotFoundException("Файл не найден");  <-- Неправильно: сообщение в исключении не на английском языке
```
Исключение это не просто телеграмма, которая летит сквозь слои.

У exception особое назначение- если исключение вылетит и не будет перехвачено внутри программы, то аварийно прекратит выполнение программы.  
Тогда на экране будет распечатано сообщение эксепшена, и это сообщение должно быть понятно сисадмину в любой точке планеты.  
А значит, сообщение должно быть на английском.

Интерпретация исключения и перевод его на локальный язык должны происходить там, где это соответствует архитектуре программы.  
Или не происходить вовсе, если исключение не планируется перехватывать.

**4. class GallowsRenderer**

+ 👍 Хорошо, что картинки и метод их выдачи вынесены в отдельный класс. Это разгружает классы с логикой от графики.

- Этот класс не рендерер- он ничего не печатает.

Это хранилище картинок. Почему бы и нет, но тогда нужно нейминг согласовать с тем, что реально делает класс
```java
public class GallowsRenderer {
  private static final String[] GALLOWS = {/* КАРТИНКИ ВИСЕЛИЦЫ*/};

  public static String render(int mistakeCounter) {
    //...
    return GALLOWS[mistakeCounter];  <-- НЕ ПЕЧАТАЕТ КАРТИНКУ, ПРОСТО ВОЗВРАЩАЕТ ЕЁ
  }
}

//ПРАВИЛЬНО:
public class PictureStorage {
  private static final String[] GALLOWS = {/* КАРТИНКИ ВИСЕЛИЦЫ*/};

  public static String get(int mistakeCounter) {
    //...
    return GALLOWS[mistakeCounter];  <-- НЕ ПЕЧАТАЕТ КАРТИНКУ, ПРОСТО ВОЗВРАЩАЕТ ЕЁ
  }
}
```

Но лично мне больше нравится, когда этот класс не просто хранилище картинок, а рендерер:
```java
public class GallowsRenderer {
  private static final String[] GALLOWS = {/* КАРТИНКИ ВИСЕЛИЦЫ*/};

  public static void render(int mistakeCounter) {
    String picture = GALLOWS[mistakeCounter];
    IO.println(picture);
  }
}
```

- Соблюдай требования утилитных классов. 

Это утилитный класс, он содержит только статические методы.  
Утилитные классы, как и классы констант, должны быть `final` и иметь приватный конструктор.  
Не должно быть возможности унаследоваться от утилиты или сделать ее экземпляр.

*Блох, "Java. Эффективное программирование", изд.3, гл.2.4*

- Неправильная реакция на ошибки.

Есть три основных реакции на ошибки: игнорирование, исправление, падение.  
Здесь выбрано игнорирование: при получении некорректного номера картинки, вместо возврата картинки виселицы метод возвращает сообщение об ошибке
```java
public static String render(int mistakeCounter) {
  if (mistakeCounter < 0 || mistakeCounter >= GALLOWS.length) {
    return "Ошибка при отображении виселицы";
  }

  return GALLOWS[mistakeCounter];
}
```

Правильная реакция здесь должна быть другой, нужно сделать быстрое падение:
```java
public static String get(int mistakeCounter) {
  return GALLOWS[mistakeCounter];  <-- КИНЕТ ИСКЛЮЧЕНИЕ, ЕСЛИ КАРТИНКИ С ТАКИМ НОМЕРОМ НЕТ В МАССИВЕ
}
```
Потому что запрос картинки с неправильным номером означает, что в алгоритме игры есть баг.  
Правильно работающий алгоритм не будет пытаться получить картинку с несуществующим номером.

Этот баг не нужно маскировать, его нужно максимально быстро выявить и устранить.  

**5. class GameSession**

- Позиционирование.

Мне непонятно позиционирование этого класса.

Возможно этот класс задумывался для хранения основной игровой логики, а поэтому вспомогательные операции типа чтения файла и рисования картинок вынесены во вспомогательные классы.  

Если так, то сейчас основная игровая логика разделена на два класса: этот и `Main`.  
Тогда эту логику нужно объединить в одном классе.  
А в Main'e оставить только диалог "Играть или выйти", конструирование системы и её запуск.  
И полностью убрать из `Main` логику управления ходом игры.

Если же этот класс задумывался как движок игры, тогда этот класс должен содержать только ту логику, которая не зависит от представления. 
То есть, движок не должен ничего печатать в консоль.  
А та часть игровой логики, которая что-то печатает в консоль, должна быть вынесена в другой класс- контроллер.

Но сейчас `GameSession` зависит от представления- печатает в консоль
```java
IO.println(GallowsRenderer.render(mistakeCounter));
```

Короче, нужно определиться с позиционированием класса.

Если он должен хранить всю основную игровую логику, пусть хранит её всю. В том числе ту её часть, которая сейчас сидит в классе `Main`.   
Если он должен быть игровым движком, то должен в себе содержать всю основную игровую логику, которая не зависит от представления и ничего не печатает в консоль.

- Нарушение SRP.

Main должен только сконфигурировать зависимости и запустить программу.  
Управлять работой программы этот класс не должен.  
В Main'e возможен только диалог "Играть или выйти"- это все ещё относится к ответственности конструирования и запуска системы.

*Мартин, "ЧК", гл.11, "Отделение конструирования системы от ее использования"*

- Большой божественный метод main.

Божественные методы разделяй на маленькие методы, каждый из которых должен делать одно дело на одном уровне абстракции:
```java
void main() {
  WordRepository repository = new WordRepository();
  Scanner scanner = new Scanner(System.in);
  boolean isRunning = true;

  while (isRunning) {
    IO.println("Чтобы начать игру нажмите - 1, чтобы выйти из игры нажмите - 0");
    String input = scanner.nextLine().trim();

    if ("0".equals(input)) {
      isRunning = false; // Выходим из внешнего цикла
      IO.println("Спасибо за игру!");
    }
    //много кода
  }
}

private static final String QUIT = "0"
```

## ВЫВОД

Если планировался объектно-ориентированный стиль, то программа в ООП стиле должна быть декомпозирована по правилам ООП и использовать ООП-подход для реализации типичных задач.  
Эта реализация имеет признаки и процедурного и объектно-ориентированного стилей.

Признаки ООП:  
🔹 Программа разделена на классы, каждый из которых (или почти каждый) описывает отдельную сущность: репозиторий, хранилище картинок и т.д.  

Признаки процедурного стиля:  
🔸 Не выявлены и не сделаны в виде классов менее очевидные, чем репозиторий, сущности. Например, "Секретное слово".  
Значит нет системного понимания объектно-ориентированной декомпозиции.

🔸 Те классы, на которые сейчас поделена программа, могут быть и в процедурной программе- процедурный стиль сам по себе не отрицает возможность создания нескольких классов.
🔸 Main, который не просто собирает и запускает игру, а управляет процессом игры.

В целом код в программе простой и понятный, написан хорошо.
